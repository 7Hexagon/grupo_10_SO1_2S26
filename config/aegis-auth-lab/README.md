# Aegis Auth Lab: instalación y persistencia

El backend Python se ejecuta como `aegislab` y recibe HTTP mediante `/run/aegis-web/http.sock`, creado por systemd con modo 0660 y grupo `admin_aegis`. No abre un puerto TCP en LFS. El puente, activado por otro socket Unix, corre como root para acceder a `/run/aegisd.sock`, verifica el UID del cliente y limita el protocolo a AUTH, VALIDATE, STATUS y REVOKE. Las decisiones de autorización corresponden a aegisd. Las unidades aplican restricciones de systemd; su configuración no equivale por sí sola a una auditoría completa de aislamiento.

El navegador de Windows accede por un proxy local que transporta las solicitudes por SSH, porque Dropbear mantiene deshabilitado el reenvío TCP. Desde la raíz del repositorio se inicia con `python src/aegis-auth-lab/windows_ssh_proxy.py` y se abre `http://127.0.0.1:8787/`; requiere la clave SSH y el helper `ssh_http_forward.py` instalado en la cuenta administrativa de la VM. Este mecanismo es solo para demostración local y no publica la aplicación en Internet. Los tokens de aegisd y las sesiones web permanecen en memoria. Cerrar una sesión web de operador no revoca su credencial: aegisd solo permite revocarla a un administrador.

La red conserva `192.168.56.111/24` en host-only y usa DHCP en el adaptador NAT. El archivo `20-aegis-nat.network` identifica su MAC; la configuración actual usa `nameserver 10.0.3.3` en `/etc/resolv.conf`, con `dns` en la entrada `hosts` de NSS. `systemd-resolved` permanece desactivado.

## Inicio y recuperación

Las unidades `aegis-lab-relay.socket`, `aegis-lab-web.socket` y `aegis-lab-web.service` están habilitadas para el arranque. Sus estados se consultan con `systemctl status aegis-lab-relay.socket aegis-lab-relay.service aegis-lab-web.socket aegis-lab-web.service`; el servicio del puente se activa cuando llega una solicitud al socket. Se pueden detener con `systemctl stop aegis-lab-web.service aegis-lab-web.socket aegis-lab-relay.service aegis-lab-relay.socket` y volver a iniciar con `systemctl start aegis-lab-relay.socket aegis-lab-web.socket aegis-lab-web.service`.

El snapshot apagado `pre-unix-reloj-20261125` conserva el estado anterior a la migración. Las copias de la web y unidades previas están en `/root/aegis-unix-web-backup-20261125/`; el binario anterior de aegisd está en `/root/aegis-clock-backup-20261126-retry/aegisd-old`. La reversión requiere detener las unidades afectadas, restaurar las copias verificadas, ejecutar `systemctl daemon-reload` y volver a iniciarlas. Al reiniciar aegisd se invalidan sus sesiones en memoria. No restaurar archivos de usuarios o contraseñas a ciegas.

Las auditorías posteriores a la instalación y al reinicio registraron 8 PASS, 0 FAIL y 0 WARN; informes `auditoria/aegis-lab/socket-unix-reloj-20261126.txt` y `auditoria/aegis-lab/socket-unix-reinicio-20261126.txt`. Después de reiniciar se comprobó desde Chrome la validación de admin_demo y el rechazo de la revocación por operador_demo.

El registro mostró un salto hacia atrás coincidente con la sincronización inicial de systemd-timesyncd; en el reinicio posterior se observó un ajuste NTP cercano a -23 horas. La causa de la divergencia inicial del reloj no está determinada. Una prueba aislada confirmó que el aegisd anterior podía prolongar tokens si retrocedía el reloj de calendario. La corrección compara vencimientos con `CLOCK_BOOTTIME`, conservando `vence_unix` para presentación. En la prueba aislada se simuló el salto sin cambiar la hora de la VM: el binario anterior prolongó el token y el corregido lo rechazó al vencer. El primer intento de instalación se revirtió por una comprobación del socket demasiado temprana; se corrigió la espera antes de instalarlo. La interfaz aún usa la hora de calendario para su sesión y podría cerrarla anticipadamente ante un salto hacia adelante; el servidor aegisd sigue siendo quien autoriza las operaciones. Queda pendiente una revisión más profunda del confinamiento del puente y protección frente a abuso antes de habilitar acceso remoto. No hay HTTPS entrante ni publicación externa.
